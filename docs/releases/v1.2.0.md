# Vector Engine v1.2.0 (in progress)

## Release summary

v1.2.0 adds `ivf`, a pure-numpy approximate-nearest-neighbor backend. It exists to close a real gap: `faiss-cpu` has no wheel for macOS arm64 (see `docs/troubleshooting` notes in `README.md`), so hosts on Apple Silicon previously had no ANN option at all — only exact `bruteforce` search. `ivf` needs no extra dependency beyond the existing numpy core requirement.

## Design

- Coarse quantizer: vectors are clustered with a pure-numpy Lloyd's k-means (`vector_engine/backends/ivf.py`), independent of the `sklearn`-backed `vector_engine.ml.kmeans` (which stays an optional-extra convenience API, not a core dependency).
- Index-time: each vector is assigned to its nearest centroid (`n_clusters`, default `sqrt(n)`).
- Search-time: each query finds its `nprobe` nearest centroids (default `n_clusters // 8`) and is scored only against vectors in those clusters.
- Implements the same `BaseBackend` protocol as `bruteforce`/`faiss` (`build`/`add`/`search`/`save`/`load`/`capabilities`/`get_runtime_stats`), registered as `"ivf"`.
- Supports `add()` (new vectors assigned to nearest existing centroid, no re-clustering) and full `save`/`load` persistence. Does not support delete (consistent with `bruteforce`/`faiss` today).

## Known limitation (measured, not hidden)

The current `search()` implementation scores each query's candidate cluster with a per-query Python loop, rather than a single batched matmul across all queries. That means:

- At **low `nprobe`** (small candidate set per query), `ivf` is faster than `bruteforce` because it touches far less data.
- At **high `nprobe`** (probing most/all clusters), `ivf` is *slower* than `bruteforce`, because `bruteforce` scores all queries against all vectors in one vectorized matmul, while `ivf` pays Python-loop overhead per query on top of a similarly sized matmul.

This is an accurate result, not a bug — vectorizing the per-cluster scoring across queries is the natural follow-up and is scoped for a later patch, not blocking this release.

## Benchmark: recall vs. latency sweep

`scripts/benchmark_ivf.py`, `n=20,000`, `d=128`, `nq=200`, `k=10`, `n_clusters=100`, `loops=5`, `seed=7`, metric `l2`:

| nprobe | Recall@10 | Latency p95 (ms) | QPS |
| ---: | ---: | ---: | ---: |
| bruteforce (exact) | 1.000 | 280.8 | 724 |
| 1 | 0.056 | 15.4 | 13,500 |
| 4 | 0.166 | 52.2 | 3,921 |
| 8 | 0.261 | 64.8 | 3,177 |
| 16 | 0.414 | 87.1 | 2,356 |
| 32 | 0.653 | 148.6 | 1,384 |
| 100 (all clusters) | 1.000 | 321.4 | 624 |

Read this as: `ivf` is a legitimate speed win only at aggressive `nprobe` settings where recall is also low (real for approximate search generally, but this implementation's crossover point is earlier than a vectorized version would give). Users who need both high recall and higher speed than `bruteforce` should currently prefer the `faiss` backend where available; `ivf` fills the gap on hosts where `faiss-cpu` cannot be installed at all.

## Stable public surface

Adds `"ivf"` as a valid `backend` value for `VectorIndex.create(...)`. No changes to existing public API (`VectorArray`, `Metric`, `SearchResult`, `bruteforce`/`faiss` backends).

## Reproducing

```bash
python scripts/benchmark_ivf.py --n 20000 --d 128 --nq 200 --k 10 --n-clusters 100 \
  --nprobe-options 1,4,8,16,32,100 --loops 5 --seed 7 \
  --output artifacts/ivf_benchmark/ivf_benchmark.json
```
